# CLAUDE.md

## Project

NestJS + Prisma backend for Sunnsteel (workout/routine tracking). Runs on Windows 11. Start, restart and stop the dev server yourself when you need it, and say so when you do — there is no need to ask the owner first. Stop it before `npm run verify` and before any Prisma migration or `generate`, which need the query-engine DLL free.

## Database

**Local development** is a PostgreSQL 17 server owned by this machine, not a hosted provider: `localhost:5432`, database `sunnsteel`, binaries in `C:\Users\Ezequiel\pgsql`, data in `C:\Users\Ezequiel\pgdata`. It is not registered as a Windows service, so it does not come back on its own after a reboot:

```bash
"C:\Users\Ezequiel\pgsql\bin\pg_ctl" -D "C:\Users\Ezequiel\pgdata" -l "C:\Users\Ezequiel\pgdata\server.log" start
```

The same command with `stop` shuts it down, and `server.log` in that data directory is the first thing to read when a connection fails. `.env` holds the only copy of its generated password.

**Production** is Railway Postgres 17 in the `SUNS sv` project, reached over Railway's private network; the backend service composes its `DATABASE_URL` from `${{Postgres.POSTGRES_PASSWORD}}` and `${{Postgres.RAILWAY_PRIVATE_DOMAIN}}`. **There is no public TCP proxy**, so the database is unreachable from a developer machine by design. Working with production data means taking a dump through Railway, never repointing `.env` at it.

The **backend service itself is public** at `https://sunnsteel-backend-production.up.railway.app` (port 4000, healthcheck `/api/health`), and the Railway API is reachable through the authenticated Railway MCP connector — deploy status, service config and logs are readable without touching the database. Read those rather than guessing at production state.

**A red CI run does not fail the deploy — it silently skips it.** The service
has `checkSuites: true`, so Railway waits for the GitHub check suite and marks
the deployment `SKIPPED` when it is red. Production then stays on the previous
commit with nothing that looks like a failure. After any push, confirm the
deployment reached `SUCCESS`; a green `git push` proves nothing. This is a good
property — it is what kept a four-day-stale production from taking a broken
migration — but only if somebody checks.

**Migrations run before the deploy goes live, not at boot.** `railway.json` sets `preDeployCommand` to `npx prisma migrate deploy`; a migration that fails there aborts the deploy and the running version keeps serving. `startCommand` is `npm run start:prod`, which does **not** migrate. Confirmed working on 2026-09-21: the deploy logged `migrate deploy` at 11:57:16 from the hook and the service started at 11:57:28. **Never move migrations back into the start command**: a failure there is an outage rather than a failed deploy, because `restartPolicyType: ON_FAILURE` retries the boot ten times with the service down. `npm run deploy` still exists for running both by hand.

Until 2026-09-20 both ran against a single hosted Neon database; that project is deleted, and a reference to Neon anywhere is stale. The split has a consequence worth holding on to: **local data no longer mirrors production**, and `prisma migrate reset` or a destructive script is now safe to run locally, which it was not while `.env` pointed at the deployment database. Local started from a dump of that shared database, kept at `C:\Users\Ezequiel\pgdata-backup-neon-2026-09-20.dump`.

## Architecture

### Module layout

Feature modules under `src/` (auth, users, exercises, routines, schedule, notifications, activity, workouts, metrics, health, common, database). `DatabaseService extends PrismaClient` (`src/database/database.service.ts`) is exported via `DatabaseModule` and injected everywhere Prisma access is needed. Controllers share the `RequestWithUser` type from `src/common/types/request-with-user.ts` rather than redeclaring it.

### Auth (Supabase)

- Supabase Auth issues JWTs; `SupabaseJwtStrategy`/`SupabaseJwtGuard` (`src/auth/strategies`, `src/auth/guards`) validate bearer tokens and sync the user into the local DB.
- Protect endpoints with `@UseGuards(SupabaseJwtGuard)`.
- **Tokens are verified locally, never with a call to Supabase Auth (TD-43).**
  `SupabaseService.verifyToken` runs `supabase.auth.getClaims`, which checks the
  ES256 signature against the project's JWKS (fetched once per process, kept
  ten minutes, refetched for an unknown key id) and `exp`, then
  `identityFromClaims` ([src/auth/access-token-claims.ts](src/auth/access-token-claims.ts))
  requires the project's issuer, the `authenticated` audience and role, and a
  subject -- `getClaims` checks none of those. Never decode a token without
  `getClaims` first. Identity, email and name come from the claims; the local
  lookup by `supabaseUserId` stays uncached (1.8 ms p50, measured). The
  trade-off is revocation: a token stays accepted until `exp` after its
  session ends, and an email change reaches the local row on the next token
  refresh. Restoring `getUser` in the guard puts ~260 ms and a Supabase Auth
  dependency back on every request; `scripts/supabase-auth.test.ts` asserts
  there is no `/auth/v1/user` call for an existing account. **The one remote
  call is on a lookup miss (TRUST-01):** before linking or creating an account,
  `getOrCreateUser` asks `getUser` whether the sign-in still exists and is the
  one the claims name. A first sign-in pays it once; without it a deleted
  member's unexpired token would recreate an empty account.
- `POST /auth/supabase/verify` (`src/auth/supabase-auth.controller.ts`) verifies a token and creates the account on first sight. **It sets no cookie.** The
  `ss_session=1` marker the frontend middleware reads is the frontend's own,
  set same-origin by its `/api/session` route: a cookie in this service's
  response is scoped to this service's domain, which is a third party to the
  app, so it was never sent back and middleware never saw it. This file said
  the opposite until 2026-09-22. Do not add one here again.
- **Supabase is the whole of authentication.** TD-47 retired what sat beside
  it: `TokenModule`/`TokenService` and `@nestjs/jwt` (no callers, plus a cron
  clearing a table with no writer), `POST /auth/supabase/migrate` (unguarded,
  took email and password and returned the account id on a match — a
  credential-testing oracle), `GET /auth/supabase/profile`, `POST
  /auth/supabase/logout`, `UsersService.create`, `findByEmailWithPassword`,
  `bcrypt`, and the `RefreshToken`/`BlacklistedToken` tables with
  `User.password` (migration `20260922140000_drop_legacy_auth`; production had
  0 accounts with a password when it ran). There is no password path left —
  do not reintroduce one without a product decision.

### Workouts module — service decomposition

`workouts.service.ts` is a thin facade over single-purpose services. The session lifecycle lives under `src/workouts/services/`, barrel-exported via `services/index.ts`:

- `workout-session-start.service.ts` — starting or resuming a session; reuse refreshes `lastActivityAt`
- `workout-session-log.service.ts` — logging sets during a session
- `workout-session-finish.service.ts` — finishing a session (applies weight progression)
- `workout-session-recap.service.ts` — the reconstructible recap of one finished session
- `workout-session-substitution.service.ts` — LIVE-11 in-session exercise swaps, refused once the slot has a completed set
- `workout-session-correction.service.ts` — LIVE-17 corrections of the latest finished workout, re-deriving everything it fed

The reads, the Progress endpoints and session sharing are top-level files in `src/workouts/`, imported directly rather than through the barrel:

- `workout-session-read.service.ts` — reads/listing
- `workout-progress.service.ts` — the dashboard progress summary, read from the active timezone-matched analytics projection (`503` until it is ready)
- `workout-strength-trend.service.ts` — bounded best-set/e1RM record-frontier series from indexed `PERSONAL_RECORD` events
- `workout-exercise-performance.service.ts` — paginated terminal-session history with completed sets, snapshot context, notes and progression events
- `workout-muscle-heatmap.service.ts` — bounded 4–12-week muscle distribution from the active timezone-matched analytics projection
- `workout-volume-trend.service.ts` — bounded weekly volume and completed-set comparisons across the total, muscles, historical routines and exercises
- `workout-session-comparison.service.ts` — the latest two completed snapshots of one stable routine-day identity
- `workout-progress-timeline.service.ts` — cursor-paginated `PERSONAL_RECORD`/`PROGRESSION_CHANGED` feed; the optional `exerciseId` (EXER-01) filters on the top-level payload id both event families carry, so it walks the same owner-scoped index, and a cursor from another exercise's feed is rejected
- `workout-personal-goals.service.ts` — PROG-08 private measurable goals evaluated from bounded rollups, the streak projection and persisted records
- `workout-plateaus.service.ts` — PROG-09 plateau watch: one query over the owner's `PersonalRecord` rows and the completed loaded sets of terminal sessions in an 8-week window, evaluated by the pure `evaluatePlateaus` against the `PLATEAU_*` contract thresholds and the account's `User.plateauMinSessions` (PREF-05: default 4, a 3–8 check constraint in migration `20260914210000_plateau_min_sessions`, also applied by `scripts/prepare-analytics-test-db.ts`, and saved through `PUT /users/preferences/plateaus` in `src/users/plateau-preferences.service.ts`); a lift whose estimated 1RM rose is never flagged
- `workout-training-signals.service.ts` — PROG-10 training signals: one query over the completed sets of the owner's finished and ended-early workouts that ended in the last two `TRAINING_SIGNAL_PERIOD_DAYS` periods (28 days), plus those workouts' snapshots for their rep targets, evaluated by the pure `evaluateTrainingSignals`: average RPE on the lifts rated in both periods, sets short of their snapshot floor (a fixed target's reps, a range's minimum), lifts whose best estimated 1RM fell in each of their last two sessions, and workouts with a completed set. Deload sessions count only as workouts, a workout with no completed set is not counted, the `TRAINING_SIGNAL_*` thresholds travel with every response, and nothing names a cause
- `workout-deload-suggestion.service.ts` — INTEL-02 deload suggestion: reads the PROG-10 inputs once over 35 days and runs the same `evaluateTrainingSignals` for today and for `DELOAD_SUGGESTION_EARLIER_DAYS` (7) ago; a load signal (effort, rep targets or declines, never workouts) marked in both, or two marked today, is sustained. It then refuses while any deload is in force or planned or one ended within `DELOAD_SUGGESTION_COOLDOWN_DAYS` (21), picks the active routine with the most workouts in the last 14 days, starts today (tomorrow when that routine was trained today) for the ROUT-16 default 7 days cut at a block boundary, and requires something planned in that window (`routinesPlannedOn`, or a rotation without training weekdays). It returns the ROUT-16 default loads and sets and creates nothing: the member saves the deload in the existing dialog. Every refusal is a stated `unavailable` reason
- `workout-block-comparison.service.ts` — PROG-11 training-block comparison, served by `TrainingBlockComparisonController` at `GET /routines/:id/training-blocks/:seriesId/comparison` beside the routine's own block routes: a started block (up to today while it runs) beside the block before it on the same routine, or the same number of days before it for the first block, a running block cutting the earlier period to the days elapsed and each capped at `TRAINING_BLOCK_COMPARISON_MAX_DAYS` (365). It reads that routine's completed sets through the PROG-10 `readInputs` (with its `routineId` filter), places each by its owner-local end date and reuses PROG-10's `effortSignal` and `repTargetSignal` across the two periods; planned workouts come from `routinesPlannedOn` up to today (null for a rotation without training weekdays), deload workouts count as workouts but stay out of effort, rep targets and lifts, and lifts trained in both are listed alphabetically by best estimated 1RM. Nothing is ranked; another member's routine answers 404 and a block not yet started 400
- `workout-session-share.service.ts` — SOC-07 revocable, field-scoped session share links

Active workout sessions are recoverable user data. Do not restore a timer that
silently marks stale sessions `ABORTED`: LIVE-10 deliberately leaves them active
until the owner resumes, completes the saved work, or discards it. Staleness is
derived by the frontend from the existing `lastActivityAt`/`startedAt` fields;
resuming through `POST /workouts/sessions/start` refreshes `lastActivityAt`.

When adding workout behavior, add a new focused service (or extend the matching one above) rather than growing `workouts.service.ts` or `WorkoutsController` directly.

### Progression schemes

Progression is tracked **per exercise** (`RoutineExercise.progressionScheme`), never per routine. The backend accepts three live schemes, enforced by `LIVE_PROGRESSION_SCHEMES` in `src/routines/dto/create-routine.dto.ts`:

- `NONE` — no automatic progression
- `DOUBLE_PROGRESSION` — increase reps first, then weight once all sets hit target
- `DYNAMIC_DOUBLE_PROGRESSION` — each set progresses independently

Progression is applied on session finish in `workout-session-finish.service.ts`. **Only a completed set carries its logged weight into the routine (TD-49):** `carryLoggedWeight` in [progression-changes.ts](src/workouts/progression-changes.ts) requires `isCompleted`, the same condition `hitTarget` uses, so a weight typed or filled into a set that was then skipped never becomes the next workout's prescription. A LIVE-17 correction re-derives through the same rule, so ticking a set there carries its weight and unticking one restores the prescription.

⚠️ Reps-to-Failure (RtF / `PROGRAMMED_RTF`) was removed from the backend and shared contracts. The Prisma enum may still carry `PROGRAMMED_RTF`/`PROGRAMMED_RTF_HYPERTROPHY` values until the DB migration lands — do not wire them back up. The DTO restricts accepted schemes to the three above regardless of the database enum.

### Shared contracts

DTOs/enums are sourced from the published `@sunsteel/contracts` package rather than redefined — check `src/routines/dto/*` and `src/workouts/dto/*` for examples before adding new shapes. Do not switch the dependency to a local `file:` link: update `../sunnsteel-contracts`, publish a new registry version, and then bump this repository to that version.

**Response serialization boundary.** Read/mutation endpoints return the shared _response_ contract types (`Routine`, `WorkoutSession`, `UserProfile`, etc.), not raw Prisma results. Each domain has a mapper that is the single place converting Prisma `Date` → ISO string and asserting, at compile time, that the response matches the contract: `src/routines/routine.mapper.ts`, `src/workouts/workout-session.mapper.ts`, and `mapUserProfile`/inline mappers in `src/users/users.service.ts`. Mapper inputs are typed via `Prisma.*GetPayload<{ select: typeof SOME_SELECT }>` so a select/contract drift breaks the build. When adding an endpoint that returns a persisted entity, map it through (or add) one of these rather than returning the Prisma object directly.

**Profile privacy is an authorization boundary, not a presentation filter.** `User` stores independent `PUBLIC`/`FOLLOWERS`/`PRIVATE` settings for biography, location, training identity, workout history, records, routines, achievements and body metrics, all defaulting to `PRIVATE`. `src/users/profile-privacy.ts` is the central owner/follower/public resolver. `getPublicProfile` must resolve access before issuing biography, location, training-identity, analytics, personal-record or body-metric reads, and `PublicUserProfile` must never include email. Denied biography/location/training-identity values are not selected or serialized. Owners always retain access; `FOLLOWERS` means the viewer follows the profile owner. `GET /users/:identifier` supplies the authenticated owner/follower context; unguarded `GET /profiles/:identifier` passes a null viewer, never queries a follow relation, exposes only `PUBLIC` sections and sends `Cache-Control: no-store`. Favorite exercises use an ordered relation to catalog `Exercise` rows rather than free text. `FeaturedProfileItem` stores at most six ordered `RECORD`, `ACHIEVEMENT`, `RANK` or `ROUTINE` references per user; replacement is atomic, accepts only current records, earned achievements and rank definitions through the current non-regressing rank, and permits at most one rank. Public reads resolve each kind only through its existing records or achievements visibility rule while omitting stale references.

**Discovery controls filter search, not direct profile reads.** `discoverableByName` and `discoverableByUsername` default to `true`; `discoverableByContacts` defaults to `false` and is only persisted for a future contact-matching feature. `searchUsers` gates its name and username branches independently. Do not apply those flags inside `getPublicProfile`: direct routes still resolve and the profile privacy boundary decides which sections are readable.

**Relationship lists are identity-only and signed-in only.** `GET /users/:identifier/followers|following|mutuals` (`src/users/user-relationships.service.ts`) page through `UserFollow` newest first with an opaque `createdAt|userId` cursor and return `RelationshipMember`: the `UserSearchResponse` identity plus the viewer's `isFollowedByMe`/`followsMe` flags, never email or any privacy-governed section. `mutuals` is viewer-relative (followers of the profile whom the viewer follows). Any authenticated member may read them, like the counts; they are deliberately absent from the unguarded `/profiles` read. `GET /users/me/suggestions` ranks follow-backs first, then accounts followed by the viewer's follows, reading at most 200 candidates of each kind. Network candidates must allow name or username discovery; follow-backs are exempt because they already appear in the viewer's follower list. There is no per-profile relationship privacy setting yet — adding one needs a new column and migration.

**Session share links are revocable, field-scoped and token-only.** SOC-07 stores `SessionShare` rows (`src/workouts/workout-session-share.service.ts`): an owner-created 144-bit base64url token for one completed session plus the selected `SessionShareField`s. Owner routes under `/workouts/sessions/:id/shares` create (at most 10 active links per session), list and revoke; revocation sets `revokedAt` and is permanent. Unguarded `GET /shared/sessions/:token` (`session-shares.controller.ts`) resolves only active tokens, rebuilds the recap through `WorkoutSessionRecapService` and serializes only the selected fields plus the owner's name, username, avatar and weight unit through `projectSharedRecap`; unselected fields are omitted rather than nulled, and it sends `Cache-Control: no-store`. The previous-session comparison is never shared. Profile privacy does not gate a share: creating one is the owner's explicit consent for that session.

**The exercise catalog carries EXER-09 metadata and has one source.** [prisma/exercise-catalog.ts](prisma/exercise-catalog.ts) holds every catalog exercise with its muscles, primary `equipment`, `movementPattern`, `mechanic`, `equipmentRequired` (the closed lowercase `EXERCISE_EQUIPMENT` vocabulary, comparable with PREF-01 location equipment) and `substitutionGroup` (near-identical exercises; every group stays within one movement pattern). `add-exercises.ts` upserts from it, and `buildExerciseMetadataSql()` generated the UPDATE backfill in migration `20260913200000_exercise_metadata`; `scripts/exercise-catalog.test.ts` fails if the catalog and that migration drift. Adding or reclassifying catalog exercises in production therefore needs a new migration generated the same way, not only a seed run. `instructions` and `mediaUrl` exist but stay empty until the content work in EXER-03/EXER-04. `GET /exercises` returns the `Exercise` contract through `mapExercise` (`src/exercises/exercises.service.ts`), which drops equipment values outside the vocabulary. Private per-account stars (EXER-07) live in `StarredExercise` (migration `20260914160000_starred_exercises`, also applied by `scripts/prepare-analytics-test-db.ts`) behind `GET /exercises/starred` and `PUT`/`DELETE /exercises/:id/star` (`src/exercises/exercise-stars.service.ts`): idempotent, capped at `STARRED_EXERCISES_MAX` with a 409, and always answered with the whole newest-first list. They are unrelated to `UserFavoriteExercise`, the public training-identity favorites.

**Exercise substitutions are session facts beside an immutable snapshot (LIVE-11).** `WorkoutSession.exerciseSubstitutions` (JSON `SessionExerciseSubstitution[]`, migration `20260914090000_session_exercise_substitutions`) records exercises performed in place of routine slots; the snapshot stays the prescription. `PUT` and `DELETE /workouts/sessions/:id/exercises/:routineExerciseId/substitution` (`services/workout-session-substitution.service.ts`) swap or revert one slot of an active session: they capture the substitute's muscles from the catalog, refuse with 409 once the slot has a completed set, delete the slot's incomplete drafts, and with `applyToRoutine` also update the live `RoutineExercise.exerciseId`, reporting `routineUpdated`. Every reader that attributes a set to an exercise resolves the slot through [session-substitutions.ts](src/workouts/session-substitutions.ts): set-log validation and live records, finish progression (swapped slots never advance the prescription), `sessionContribution` muscle and record attribution (including analytics rebuilds through `summarizeSession`), session comparison and the session response. Recap and volume trend already name exercises from the logged set. `scripts/prepare-analytics-test-db.ts` applies this migration too; a new column read by the generated client must be added there or the integration job fails.

**Routines are weekly or a rotation (ROUT-11).** `Routine.scheduleMode` (`WEEKLY` by default, or `ROTATION`), a nullable `RoutineDay.dayOfWeek` and an optional `RoutineDay.name` (VarChar 40) arrived in migration `20260914230000_rotation_routines`, also applied by `scripts/prepare-analytics-test-db.ts`. `normalizeRoutineDays` ([src/routines/routine-schedule.ts](src/routines/routine-schedule.ts)) enforces distinct weekdays on weekly routines, no weekday on rotation days (renumbered 0..n-1 in their order), trimmed names and at most seven days; changing the mode on update requires the days. Rotation reads add `nextRotationDayId` from one lookup of the routine's last COMPLETED session per rotation routine: the day after its live day, or after the order its snapshot recorded when an edit replaced the day. History responses name days through `routineDayName` in `workout-session.selects.ts` (contracts `routineDayLabel`: name, else weekday, else rotation letter), and new snapshots carry the day's name. SCHED-07 adds `Routine.restDays` (weekdays; migration `20260915090000_routine_rest_days`, also applied by `scripts/prepare-analytics-test-db.ts`): `normalizeRestDays` refuses rest days on rotations and on training weekdays, and an update that omits them keeps the stored ones minus any that became training weekdays. SCHED-06 adds `Routine.rotationWeekdays` (migration `20260915170000_rotation_weekdays`, also applied by `scripts/prepare-analytics-test-db.ts`): the weekdays a rotation trains on, sorted and deduplicated by `normalizeRotationWeekdays`. Weekly routines refuse them (400), an update that omits them keeps the stored ones, switching to weekly clears them, and versions (ROUT-08) keep them; placing rotation days on dates is frontend-only.

**Routine versions are immutable setups beside the live routine (ROUT-08).** `RoutineVersion` rows (migration `20260915150000_routine_versions`, also applied by `scripts/prepare-analytics-test-db.ts`) store the contracts `RoutineVersionSetup` as JSON: name, description, mode, rest days and every day, exercise (its catalog id and name at the time) and set, without ids, because every routine edit replaces the days. [src/routines/routine-versions.service.ts](src/routines/routine-versions.service.ts) serves `GET`/`POST /routines/:id/versions`, `POST /routines/:id/versions/:versionId/restore` and `DELETE /routines/:id/versions/:versionId`. Saving and restoring run under the account lock; numbers come from `Routine.lastVersionNumber`, so a deleted number is never reused, and a routine keeps at most `ROUTINE_VERSIONS_MAX` (20) versions (409 beyond). A restore checks that the version's exercises are still in the catalog, saves the current setup as a `BEFORE_RESTORE` version, then applies the version through `RoutinesService.updateInTransaction`, so the ordinary update's history guards (no live session of the routine, snapshots ready) apply unchanged.

**Training blocks are dated setups, and ROUT-15 executes them through a working copy (ROUT-09/ROUT-15).** `RoutineTrainingBlock` rows (migration `20260923120000_routine_training_blocks`) are immutable revisions of a named, inclusive `YYYY-MM-DD` range whose `setup` is a `RoutineVersionSetup` captured from the live routine or a saved version; exactly one revision per `seriesId` has `supersededAt = null`, blocks of one routine never overlap, a started block only appends revisions, and only a future one can be deleted ([routine-training-blocks.service.ts](src/routines/routine-training-blocks.service.ts)). **A setup has no ids, and everything a session touches is keyed by real `RoutineExercise` ids**, so each revision is also written as a **working copy**: real `RoutineDay`/`RoutineExercise`/`RoutineExerciseSet` rows marked with `RoutineDay.trainingBlockId`, created from the setup in the same write (and backfilled for pre-ROUT-15 revisions by migration `20260923210000_training_block_execution`, also applied by `scripts/prepare-analytics-test-db.ts`, which is re-runnable because it skips revisions that already have days). That is what lets set logging, finish progression, previous performance, LIVE-11 swaps, LIVE-16 notes and LIVE-17 corrections work unchanged: a session of a block day logs against the block's rows, **progression advances the block's copy and never the baseline**, and a new revision starts again from its authored loads. The price is that **every baseline read must filter `trainingBlockId: null`** -- `ROUTINE_WITH_DAYS_SELECT`, the routine edit's `deleteMany`, activity, discovery, the routine summary, reminders, the partner schedule and schedule overrides all do; the routine-wide `@@unique([routineId, dayOfWeek])` became two partial unique indexes (baseline per routine, block per block) that Prisma cannot declare. **`resolveRoutinePlan` from contracts is the one resolver** of what a date trains -- the active block's schedule and days, else the baseline -- and the server applies it wherever it decides a plan: `WorkoutSessionStartService` resolves the owner's local date and refuses (409, `assertDayInPlan` in [session-training-block.ts](src/workouts/session-training-block.ts)) a day outside the plan in force, then copies the block's id, series, revision and name onto the session (`WorkoutSession.trainingBlock*`) and its snapshot, so a later revision or the block's end never rewrites history; `routinesPlannedOn` (NOTIF-04 reminders and the SOC-08 partner count) and moves and skips (`occurrenceRoutine`, per date, source and target separately) resolve through it via [routine-plan.ts](src/routines/routine-plan.ts). The owner's routine read (`ROUTINE_OWNER_SELECT`) carries every current revision as `Routine.trainingBlocks` with its working-copy days; a rotation continues from the last completed session **of the same plan** (`trainingBlockSeriesId`), so a block starts on its first day and the baseline resumes where it left off. Revising a block while a session of it is live is refused (409). Blocks are not in the account export yet.

**A deload is a dated, lighter copy of the plan in force, executed like a block (ROUT-16).** `RoutineTemporaryOverride` rows (migration `20260924090000_deload_overrides`, also applied by `scripts/prepare-analytics-test-db.ts`; idempotent, it also narrows the baseline weekday index to rows with neither marker and adds one per override) store kind `DELOAD`, an inclusive `YYYY-MM-DD` range, the chosen `loadReductionPercent` (0/10/20/30/40) and `setMode` (`ALL`/`HALF`), where the prescription came from (`BASELINE`, or a `TRAINING_BLOCK` series and name), the `originalSetup` captured and the lighter `setup` -- and, like a block revision, a **working copy** of real days marked `RoutineDay.temporaryOverrideId`, so **every baseline read now filters both markers**. [routine-deloads.service.ts](src/routines/routine-deloads.service.ts) serves `GET`/`POST /routines/:id/deloads`, `POST /routines/:id/deloads/:overrideId/end` and `DELETE /routines/:id/deloads/:overrideId` under the account lock: create captures what the start date trains -- the block's working copy with its progressed loads and the block's schedule, or the routine -- and makes it lighter with contracts' `applyDeload`, the same rule the frontend previews (nearest step on the exercise's own increment, a load the grid cannot cut keeps its weight, `HALF` keeps the first half of each exercise's sets, and an unchanged copy is refused 400 with `DELOAD_NOT_LIGHTER`). The pure rules are in [routine-deloads.ts](src/routines/routine-deloads.ts): `assertDeloadDates` refuses a range that starts before the owner's local today, lasts over `DELOAD_MAX_DAYS` (14), overlaps another deload of the routine or crosses a block boundary (every date must share one plan), and `assertBlockLeavesDeloads` makes a block create, revise or delete refuse to change the plan under an unfinished deload unless it is the same series and still contains it. End early works only on an active deload and moves its end to yesterday (`endedEarlyAt` records it); cancel works only on one that has not started and deletes it with its copy. `resolveRoutinePlan` gives a deload in force precedence and still reports the block it lightens, so the start (`assertDayInPlan`: during a deload only its days; outside it none of them), NOTIF-04 reminders, the SOC-08 partner count and SCHED-04/05 moves and skips (`PLAN_OVERRIDES_SELECT`/`toPlanOverrides` in [routine-plan.ts](src/routines/routine-plan.ts)) all follow it. A session records `temporaryOverrideId`/`temporaryOverrideKind` and its snapshot the same, and **`progressionRuns` skips progression for it at finish and when a LIVE-17 correction re-derives**, so a deload never moves the loads of the plan it lightened. Its rotation continues the underlying plan's order (the mapper carries the plan's next day into the copy by position). The owner read (`ROUTINE_OWNER_SELECT`) carries the 26 newest as `Routine.temporaryOverrides`. Deloads are not in the account export yet, like blocks.

**Schedule overrides are the schedule-instance model (SCHED-04).** `ScheduleOverride` rows (migration `20260915190000_schedule_overrides`, also applied by `scripts/prepare-analytics-test-db.ts`) change one routine's plan on one calendar date (YYYY-MM-DD strings, unique per routine and date), because routine edits replace the days and a date is the only stable identity. Kind `MOVE` puts a weekly occurrence on `toDate`; kind `SKIP` (SCHED-05, a new enum value in migration `20260915210000_schedule_skip`) marks it skipped, with no target. [src/schedule/schedule-overrides.service.ts](src/schedule/schedule-overrides.service.ts) (in `ScheduleOverridesModule`, not `ScheduleModule`, which is `@nestjs/schedule`'s) serves `GET /schedule/overrides?from&to` (at most `SCHEDULE_OVERRIDES_MAX_RANGE_DAYS`, matching either the date or the target), `PUT /schedule/overrides/move` (an upsert under the account lock, so moving again changes the target), `PUT /schedule/overrides/skip` (the same upsert, so skipping a moved workout skips the occurrence and frees the day it moved to) and `DELETE /schedule/overrides/:id`. The pure `assertMovable` refuses rotations, dates the routine does not train on, moves beyond `SCHEDULE_MOVE_MAX_DAYS`, past dates (with one day of slack, since the server does not know the device's time zone) and targets the routine is already planned on or another of its moves took (409); a date whose own workout moved away or was skipped is free. `assertSkippable` refuses dates more than `SCHEDULE_SKIP_PAST_DAYS` back (with the same slack) and never a rotation. The schedule itself is built in the frontend.

**Owner notifications are gathered on read (NOTIF-01).** `Notification` rows (migration `20260915230000_notifications`, also applied by `scripts/prepare-analytics-test-db.ts`) belong to a recipient and are unique per `sourceKey`. [src/notifications/notifications.service.ts](src/notifications/notifications.service.ts) serves `GET /notifications`, which first gathers, through the pure `gatherNotifications` ([notification-sources.ts](src/notifications/notification-sources.ts)), the owner's `ACHIEVEMENT_UNLOCKED` events that were not backfilled, one note per terminal session with `PERSONAL_RECORD` or `PROGRESSION_CHANGED` events (named from its snapshot) and new `UserFollow` rows (keyed by their time, so a refollow is announced again), all from the last `NOTIFICATIONS_LOOKBACK_DAYS`, with `createMany({ skipDuplicates: true })`; it drops rows past `NOTIFICATIONS_RETENTION_DAYS` and returns the newest `NOTIFICATIONS_LIST_LIMIT` active rows with the unread count and each follower's current identity and follow-back state. `POST /notifications/read` marks the given ids (UUIDs, at most the list limit) or every active one read. Those original sources remain branches in the gatherer; NOTIF-07 adds the first separately synchronized notification source. Deleting an account or a session cascades to its notifications.

**Selected partner activity is opt-in and re-authorized continuously (NOTIF-07).** Migration `20260924100000_partner_activity_alerts` adds the two off-by-default categories and their enable instants, the `TRAINING_PARTNER_SESSION`/`TRAINING_PARTNER_ACHIEVEMENT` kinds, `pushProcessedAt` and `revokedAt`. [src/notifications/partner-activity-alerts.service.ts](src/notifications/partner-activity-alerts.service.ts) runs a minute sweep and a `GET /notifications` catch-up. It creates at most one row for a completed session and one for a live-earned non-streak achievement, never for each record or progression change, and only after the recipient enabled that category. Eligibility requires the actor's current activity audience, a directional `activity` grant to the recipient, an active partnership and no block or moderation hide. Losing any boundary revokes the durable row immediately; restoring it unrevokes the same `sourceKey`, preserving its push claim so it cannot notify twice. Delivery claims unprocessed active rows atomically with `FOR UPDATE SKIP LOCKED`, then uses the ordinary category, quiet-hours and device controls.

**Web Push is optional infrastructure with one payload so far (NOTIF-08/NOTIF-03).** `PushSubscription` and `ScheduledPush` rows (migration `20260917074329_push_delivery`, also applied by `scripts/prepare-analytics-test-db.ts`) back `src/notifications/push/`. `PushConfigService` reads `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`; **without them the server keeps working and every read reports push unavailable**, so no client is prompted for a permission that could not be honoured. `PushSubscriptionsService` serves `GET`/`POST`/`DELETE /notifications/push/subscriptions`: registration is idempotent on the endpoint (a browser returns the same one every start), the newest `PUSH_SUBSCRIPTIONS_MAX` devices are kept, and **the endpoint is never returned to a client** because it is the capability to push to that device. `PushSenderService` sends to every device of one account and retires a subscription only on 404/410 — a 429 or 5xx may succeed next time. `RestAlertService` (`PUT`/`DELETE /workouts/sessions/:id/rest-alert`, exported to `WorkoutsModule`) schedules at most one alert per session: a new rest period replaces the last, `REST_ALERT_MIN_LEAD_SECONDS` refuses anything the sweep could not beat, and a refusal is reported as a stated `reason`, never as a silent success. `ScheduledPushService` sweeps every `PUSH_SWEEP_INTERVAL_MS` with `DELETE ... RETURNING`, which claims rows atomically so two instances cannot both send one alert; a pending alert is a row, not a timer, so a restart still delivers it. The alert body is static by necessity — the Web Notifications API has no chronometer field, so **nothing may promise a ticking countdown**.

**Notification controls and training reminders (NOTIF-05/NOTIF-04).** `User` gained `notifyRestAlert`, `notifyTrainingReminder`, `quietHoursStartMinute`, `quietHoursEndMinute` and `reminderMinuteOfDay` (migration `20260917140000_notification_preferences`, also applied by `scripts/prepare-analytics-test-db.ts`, with CHECK constraints bounding every local minute to 0-1439 and pairing both ends of the window). It was written by hand rather than generated because `ScheduledPush.dedupeKey` had to be backfilled before it could be made unique; that key replaced a unique `sessionId`, which a reminder has none of. `NotificationPreferencesService` serves `GET`/`PUT /notifications/preferences`; a partial write keeps what it omits, and clearing a window is sending `quietHours: null`, which is deliberately different from omitting it. Turning a category off also deletes that category's pending rows, so the next notification does not arrive after the switch. **`suppressionFor` is the single place both controls are applied**, called from `PushSenderService` at send -- not at schedule -- because a rest alert set before quiet hours begin still arrives inside them, and a category switched off afterwards must stop a push already waiting; `RestAlertService` also asks early so it can refuse with `CATEGORY_OFF` or `QUIET_HOURS` instead of accepting and dropping it. `TrainingReminderService` chooses **one** payload per account per local date -- NOTIF-06 streak-at-risk takes precedence over the NOTIF-04 reminder and replaces it, sharing the same per-date key so two pushes about one day are impossible. `streakAtRisk` ([streak-risk.ts](src/notifications/push/streak-risk.ts)) fires only three days after the last session, because `nextStreak` continues a run across a gap of at most three days: earlier nothing is at stake, later the run has already ended. The planner ticks every five minutes over accounts that chose a time, left the category on, registered a zone and have a subscribed device, and enqueues one `ScheduledPush` keyed `reminder:<local date>` when the current local minute falls inside a ten-minute catch-up window. **It reminds at a chosen time on training days, never "before your session":** a routine day carries a weekday and nothing stores an intended hour, so there is no session time to count back from. `routinesPlannedOn` ([training-days.ts](src/notifications/push/training-days.ts)) is the schedule rule ported from the frontend's `buildScheduleWeek` -- archived routines and rotations without training weekdays plan nothing, rest days are a plan not to train, moves and skips apply, and a date already trained is dropped. [local-time.ts](src/notifications/push/local-time.ts) only ever reads the wall clock forwards; mapping a chosen local minute back onto an instant would fire twice or never on the two daylight-saving days a year.

**Routine sharing exposes the prescription, never the training (ROUT-04).** `Routine.visibility` (`RoutineVisibility`: PRIVATE by default) and `RoutineShare` rows arrived in migration `20260917200000_routine_sharing`, also applied by `scripts/prepare-analytics-test-db.ts`. [routine-sharing.service.ts](src/routines/routine-sharing.service.ts) serves `PUT /routines/:id/visibility`, `GET`/`POST`/`DELETE /routines/:id/shares`, unguarded `GET /shared/routines/:token` (`Cache-Control: no-store`) and the member read behind `GET /users/:identifier/routines`. **The shared payload is `captureRoutineSetup`** — the same shape ROUT-08 versions store — chosen deliberately as a safeguard: it has no field a session, record or log could occupy, where a hand-written projection could drift into carrying one. Target loads are included, because a program without them cannot be followed. **Two rules apply and `canViewRoutine` takes the narrower**: the account-level PROF-06 routines rule caps each routine's own visibility, so a per-routine switch can never widen a privacy setting made elsewhere; `scripts/routine-sharing.test.ts` checks all nine combinations against the effective visibility. A routine a viewer may not read answers 404, never 403, so it is indistinguishable from one that does not exist. A link ignores visibility entirely — it is the owner's explicit consent for that routine, exactly as in SOC-07 — and revocation is permanent.

**A featured routine is a fourth typed slot, not a second showcase (PROF-08).** `FeaturedProfileItemKind` gained `ROUTINE` in migration `20260918090000_featured_routine_kind`, also applied by `scripts/prepare-analytics-test-db.ts`; the `referenceId` is the routine's id and the resolved payload is the ROUT-04 `SharedRoutineSummary`, read through the shared [routine-summary.ts](src/routines/routine-summary.ts) select and mapper so a featured routine and a listed one can never disagree. `FeaturedProfileItemsService` asks `ROUT-04`'s rule twice over, deliberately differently: **selecting**, the owner is only offered routines whose `effectiveRoutineVisibility` is not `PRIVATE`, because featuring one nobody else can reach would show the owner a slot that is never rendered; **reading**, `canViewRoutine` decides, so the account-level PROF-06 routines rule caps each routine's own visibility and a denied slot is omitted rather than emptied. `resolveForProfile` therefore takes the viewer's owner/follower context alongside the section access flags. `GET /users/:identifier/routines/:routineId` is the member read of one such routine; it resolves the owner from the identifier first, so a routine belonging to somebody else answers 404.

**Cloning copies the prescription into an independent routine (ROUT-05).** `POST /routines/clones` takes exactly one source — a share `token` or a `routineId` — and `readCloneSource` ([routine-cloning.ts](src/routines/routine-cloning.ts)) refuses both at once rather than preferring one, because the two answer different questions about who may read the routine. The clone goes through the reads that already exist, so it can never see more than a reader can: a token through `readByToken`, an id through `readVisibleRoutine` and its 404. What is copied is `SharedRoutine.setup` put back through `setupToRoutineUpdate`, the same pair `ROUT-08` restores use, and then `RoutinesService.create`; **no third projection of a routine exists**, which is what keeps training out of a clone. The new routine starts `PRIVATE` with no links, versions, favourite or completed state — inheriting `PUBLIC` would republish somebody else's programme without anyone choosing to — and an exercise that has left the catalog is refused with `UNKNOWN_EXERCISE` rather than cloned into a day that cannot be trained. Recording where a clone came from is `ROUT-06`.

**A block is symmetric and enforced before every read (PROF-10).** `UserBlock` rows (migration `20260918140000_blocks_reports_lineage`, also applied by `scripts/prepare-analytics-test-db.ts`) are stored once, from blocker to blocked, and read as **mutual** everywhere. [member-blocks.ts](src/users/member-blocks.ts) holds the two pure where-builders and the other-party reader; **they are used directly by each service with its own `db` rather than through an injected service, deliberately**, so no wiring mistake can make a privacy control fail open. `MemberBlocksService` serves `GET`/`PUT`/`DELETE /users/me/blocks[/:identifier]`, capped at `BLOCKED_MEMBERS_MAX`, and **deletes the follow in both directions** inside the same transaction — a follower count that still includes a blocked member is the control not working. Unblocking restores nothing. Enforcement lives in `searchUsers` (both parties excluded), `getPublicProfile` (404 **before** any sensitive read, exactly as `ROUT-04` answers for a denied routine, and a 403 would confirm both the account and the block), `followUser` (the same 404), `UserRelationshipsService.list`/`suggestions`, and the `ROUT-04` member routine reads. `PublicUserProfile.moderation` reports only the viewer's own block; a profile never says it has blocked the viewer, because the viewer never gets that profile.

**A report is recorded, and TRUST-04 reads it (PROF-10).** `MemberReport` rows store the subject, a fixed `ReportReason` and optional 500-character details, capped at `REPORTS_PER_DAY_MAX` a day and refused when the subject does not exist. `POST /reports` is the only write route, and the receipt still carries an id and a timestamp and nothing about review — **a queue existing is not a timetable**, so that copy must not drift.

**Moderation is one flag, two actions and an append-only record (TRUST-04).** `User.isModerator` is the whole authorization model: there is one moderator, so a roles table would be a subsystem built for a second one who does not exist. `ModeratorGuard` ([src/moderation/moderator.guard.ts](src/moderation/moderator.guard.ts)) answers **404, not 403**, for the reason `PROF-10` and `ROUT-04` both give, and reads the flag per request rather than trusting a token claim. `prisma/seed-moderator.ts` (`npm run db:seed:moderator -- <email> [--revoke]`) grants and revokes it; it is environment data, not schema, so it is a script rather than a migration and **a database restore can silently drop the grant while keeping the column**. [moderation.service.ts](src/moderation/moderation.service.ts) serves `GET /moderation/queue`, `GET /moderation/actions` and `POST /moderation/reports/:id/{views,dismiss,hide,restore}`; the pure rules (status transitions, the cursor, page sizes) are in [moderation-rules.ts](src/moderation/moderation-rules.ts). **There is no reviewer bypass.** `resolveSubject` runs the shipped `PROF-06`/`PROF-10` rules **with the moderator as the viewer**, and a subject they may not read is returned `isWithheld` with a null title and a null owner — never filled in "for context". A moderator who hides a routine can no longer read it either; that is correct, and the enforcement record rather than a privileged read is how a decision is revisited. **Reading is an action**: `POST .../views` writes a `VIEW_SUBJECT` row before answering, and the reviewer then opens the subject's own page — there is deliberately no moderation mirror of the content, because a second read path is a second answer to "may this viewer see this". **A hide narrows the shipped rule rather than standing beside it.** `canViewRoutine` takes a required `moderation` argument (adding it is what made the compiler name every read that had to consider a hide); `Routine.moderationHiddenAt` is refused before either `ROUT-04` rule, `SessionShare.moderationHiddenAt` stops the token resolving while `revokedAt` stays null, and `User.moderationHiddenAt` answers 404 and leaves search, suggestions, relationship lists, activity and discovery. **Nothing is deleted** — the routine keeps its days, versions and links, the account keeps everything it owns and still reads its own profile — and `Routine.isHiddenByModeration`/`SessionShare.isHiddenByModeration` tell the owner, because a thing that resolves for nobody while its own control reads "Public" is a switch with nothing behind it. **`hiddenFromViewer`/`isHiddenFromViewer` in [member-blocks.ts](src/users/member-blocks.ts) answer blocks and hides together** and replaced five duplicated block lookups, so a read written later cannot honour one and omit the other; like the block builders they take the caller's own `db` rather than an injected service. **`ModerationAction` rows are never updated or deleted**: undoing a hide appends a `RESTORE_SUBJECT` row and the `HIDE_SUBJECT` row it supersedes stays exactly as written, which is the only way "the record is never editable" and "a mistaken hide is not permanent" both hold. Migration `20260920160000_moderation_foundation`, registered in `scripts/prepare-analytics-test-db.ts`.

**Account deletion is immediate and complete (TRUST-01).** `DELETE /users/me` ([account-deletion.service.ts](src/users/account-deletion.service.ts)) takes the typed username (`matchesDeletionConfirmation` from contracts: case, whitespace and a leading `@` ignored) and refuses a moderator with 409, because every `ModerationAction` cascades from its moderator and that record is append-only. **The order is the safety property:** stored avatars first (`SupabaseService.removeStoredAvatars`: the member's whole `avatars/<supabase uid>/` folder, the only place the Settings upload and the bucket's RLS let a member write -- see the frontend's `supabase/migrations/20260923103003_avatars_bucket.sql`; the service role bypasses those policies, and a missing bucket or folder holds nothing), then one transaction that deletes the `User` row, which cascades everything the member owns, and deletes the Supabase sign-in before committing. Supabase refusing rolls the account back untouched; an already-removed sign-in counts as removed so a retry finishes. **Nothing may block the cascade**: `scripts/account-deletion.integration.test.ts` walks `pg_constraint` on the fully migrated schema and fails if any foreign key into a table that cascades from `User` is `RESTRICT`/`NO ACTION` -- give a new table referencing member data `onDelete: Cascade` or `SetNull`. It runs after the analytics suite, which applies the FK cutover. What survives is what was never the member's: another member's clone keeps its content with lineage nulled, and reports **about** the member stay for the queue, which already renders a missing subject; reports the member **filed** go with the account.

**A member can take all of their data with them (EXPORT-01).** `GET /users/me/export` ([account-export.service.ts](src/users/account-export.service.ts)) answers the contracts `AccountExportV1`: one versioned JSON document (`format`, `formatVersion`; fields are only added within a version) built by **one read-only pass through the selects and mappers the app already serves** -- the profile read, `ROUTINE_WITH_DAYS_SELECT` with `toRoutineResponse`, stored version setups through `readRoutineSetup`, `buildWorkoutSessionSelect(true)` with `toWorkoutSessionResponse` -- so the file cannot describe a routine or workout differently from the screens. Weights stay kilograms (`weightsAreKilograms`). Other members appear by username and name only, and the file never carries anyone else's email, share-link tokens or push endpoints and keys; `omitted` states what is left out and why. It is throttled to five per ten minutes on the `long` throttler and sent `Cache-Control: no-store`. Measured on a real local account: 50 workouts and 573 sets in 1.0 s and 491 KB. `scripts/account-export.integration.test.ts` exports a seeded member on real Postgres and asserts every section plus the absence of another member's email, a share token and push credentials; the harness never registered the training-location and goals migrations, so that test applies them itself after the analytics suite. **A new table holding member data belongs in the export** as well as in the deletion cascade.

**Session notes are the workout's, never the routine's (LIVE-16).** `PUT /workouts/sessions/:id/notes` ([workout-session-notes.service.ts](src/workouts/services/workout-session-notes.service.ts), pure rules in [session-notes.ts](src/workouts/session-notes.ts)) is a partial write of the workout note (`WorkoutSession.notes`) and of `WorkoutSession.exerciseNotes` (JSON `SessionExerciseNote[]`, migration `20260923190000_session_exercise_notes`, also applied by `scripts/prepare-analytics-test-db.ts`), which merge by slot under a row lock so two saves cannot overwrite each other; an empty note clears it, and too long is refused rather than cut (`SESSION_NOTE_MAX_LENGTH`, `SESSION_EXERCISE_NOTE_MAX_LENGTH`). A slot must be in the session's snapshot day. Notes feed nothing derived, so they are accepted during the workout and at any time after it; only a discarded workout refuses them (409). The recap names each noted exercise as it was performed (a swapped slot by its substitute), and `projectSharedRecap` includes them only with the `notes` field. `RoutineExercise.note` is the routine's standing instruction and `PATCH /routines/:id/exercises/:exerciseId/note` still edits it, but no frontend screen calls that route any more.

**A session can take sets beyond its prescription, and they never reach progression (LIVE-15).** A set log whose `setNumber` is above the highest prescribed set of its slot -- read from the session snapshot by `prescribedSetCount` in [session-extra-sets.ts](src/workouts/session-extra-sets.ts), falling back to the live routine's sets only for a session without a snapshot -- is an **extra set**: work done today, not a change to what was prescribed, so the snapshot stays the one answer to "what was planned". There is no new column or endpoint: `PUT /workouts/sessions/:id/set-logs` already stored such rows, and now `extraSetRefusal` accepts a **new** one only as the next set after the slot's last (no gaps, so previous performance and session comparison keep matching by `setNumber`) and at most `MAX_EXTRA_SETS` (10) beyond the prescription, while an existing row keeps saving; `DELETE .../set-logs/:routineExerciseId/:setNumber` now refuses a prescribed set and any extra set but the highest (`removeSetRefusal`, 400). `setNumber` is `@IsInt` -- a decimal used to pass validation and fail at the Int column. Once completed, an extra set counts wherever completed work counts (recap, totals, analytics, live and persisted records, LIVE-17 corrections); progression and PROG-10 rep targets walk the snapshot's sets and never see it. A LIVE-11 swap deletes the slot's incomplete drafts, extras included.

**A finished workout can be corrected, and everything it fed is re-derived (LIVE-17).** `GET`/`POST /workouts/sessions/:id/corrections` ([workout-session-correction.service.ts](src/workouts/services/workout-session-correction.service.ts), pure rules in [session-correction-rules.ts](src/workouts/session-correction-rules.ts)) correct weight, reps, RPE and completion of the logged sets of the owner's **latest** completed workout, for `SESSION_CORRECTION_WINDOW_HOURS` (48) after it ends and **until any other workout starts**, at most `SESSION_CORRECTIONS_MAX` (10) times; `sessionCorrectionWindow` in contracts is the one rule and a closed window answers 409 with its `code`. That restriction is what makes it exact: nothing later has been measured against this workout, so its contribution is swapped in place under the account lock instead of replaying history. In one transaction the service rewrites the set logs, the session totals and the `SESSION_COMPLETED` payload; applies the contribution **delta** to the DAY/WEEK rollups, muscle rollups and projection (the checksum chains the correction, so a later rebuild reaches the same totals by another path); re-measures every exercise the workout touched against every other completed workout's sets -- a set that still wins keeps or gains the `PERSONAL_RECORD` event (same key, corrected payload), `PersonalRecord` and frontier, otherwise both return to the best earlier set or are removed; drops milestones this workout unlocked that the corrected totals no longer reach (and their notification) and awards new ones; re-runs its progression and rewrites the routine's sets **only while they still read what the finish wrote** (`prescriptionIntact`), reporting the rest as `progressionKept`; recounts the `SESSION_PROGRESS` notification; and deletes the reactions, comments (with their notifications) and audience overrides of any activity entry whose event it removed. **This is the one place a training event is rewritten or deleted after the fact**; keep it here. `SessionCorrection` rows (migration `20260923160000_session_corrections`, also applied by `scripts/prepare-analytics-test-db.ts`) are append-only before/after records, cascade with the session and the account, and are in the account export. It refuses (409 `ANALYTICS_REBUILDING`) while a generation is building, because that generation may already have consumed the old numbers. `scripts/session-corrections.integration.test.ts` corrects a real finished workout twice on Postgres and reads every derived row back.

**A clone records where it came from (ROUT-06).** `Routine.clonedFromRoutineId`, `clonedFromUserId` and `clonedAt` are written by `RoutineSharingService.cloneRoutine` on the clone only — the source is never told it was copied — and both references are `SET NULL`, so deleting a source never deletes somebody else's copy. [routine-lineage.ts](src/routines/routine-lineage.ts) resolves what a viewer may be told through the **same `canViewRoutine`** every other routine read uses: a clone of a routine the viewer may not read says it is a clone and reports `isSourceHidden`, because otherwise a public clone would become a way to discover that a private routine exists and who wrote it. A deleted source, a deleted author and a block all reach that same state.

**Discovery derives its facets and declares nothing on the author's behalf (ROUT-07).** `GET /routines/discover` ([routine-discovery.service.ts](src/routines/routine-discovery.service.ts)) lists what `canViewRoutine` already allows -- public routines in public accounts, followers-only ones to followers -- so **it is not a new visibility tier**, and `PROF-10` removes both parties of a block from each other's results. Four of the six facets are derived per candidate by [routine-facets.ts](src/routines/routine-facets.ts) and **never stored**: a denormalised facet drifts from the routine the moment an edit misses its recompute. `estimateDaySeconds` and its `SECONDS_PER_REP`/`SETUP_SECONDS_PER_EXERCISE` constants are `ROUT-10`'s rule ported to the server the way `NOTIF-04` ported the schedule rule, so the wizard and discovery cannot quote different numbers; a rep range is judged by its top end and the **longest** day is reported, because that is what has to fit. The other two, `Routine.goal` and `Routine.experienceLevel` (migration `20260919100000_routine_classification`, also applied by `scripts/prepare-analytics-test-db.ts`), are **owner-declared** and reuse the `PROF-05` enums: they are claims only an author can make, and deriving them from that author's training identity would attribute a person's goals to a programme. An undeclared one is unknown, not a wildcard -- a routine whose author said nothing never answers that filter. Equipment reads as what the **viewer has**, so a routine matches only when it needs nothing outside the selection and bodyweight work always matches. The scan is capped at `ROUTINE_DISCOVERY_SCAN_LIMIT` and the response reports `scanTruncated`, as `ACH-05` reports a truncated event scan; the cursor is an opaque offset into the filtered result because filtering happens after the scan. A routine with no exercises is never offered, and the owner's own routines are not discoveries.

**Activity is generated on read, and profile privacy caps it (SOC-03/SOC-04).** [src/activity/](src/activity/) stores **no entries**: [activity.service.ts](src/activity/activity.service.ts) builds them per read from `TrainingEvent` rows (`SESSION_COMPLETED`, `PERSONAL_RECORD`, `PROGRESSION_CHANGED`, `ACHIEVEMENT_UNLOCKED`, `STREAK_MILESTONE`), the shipped `comebackRecognitionSummary` over the same bounded 501-event read `ACH-05` uses, and routines with `Routine.sharedAt`. Only the owner's choices are stored (migration `20260919120000_activity_sharing`, also applied by `scripts/prepare-analytics-test-db.ts`): `ActivitySharingDefault` per type (a missing row is `PRIVATE`, so nothing reaches anyone until chosen) and `ActivityEntryOverride` per entry, keyed by the entry's stable id -- the event's `eventKey`, the comeback recognition id or `routine:<id>` -- where `PRIVATE` withdraws it. **Every rule is in [activity-rules.ts](src/activity/activity-rules.ts), pure:** `canViewActivity` is the shipped `resolveProfileViewerAccess` section check plus `canViewProfileSection` on the entry's audience, the same shape as `canViewRoutine`, so an entry can never reach past the `PROF-06` section in `ACTIVITY_TYPE_SECTIONS`; a shared routine must also pass `canViewRoutine`, which the query asks for each value a routine can hold rather than copying. `planAuthorActivity` turns one author's defaults and overrides into the types, included keys and excluded keys a query uses, and the rows are asked the same rule again after the query. Backfilled achievements and streaks never produce an entry (they have no honest date), and a streak is reported once, as `STREAK_MILESTONE`, never also as its `STREAK_DAYS` achievement. Links are resolved here, never by the client: a record links to the member's profile only while `PersonalRecord.setLogId` still matches the event, and a session or load progression, which no page shows another member, has none. `GET /activity/feed` reads the members the viewer follows (at most `ACTIVITY_FEED_FOLLOWED_MAX`, reporting `followedTruncated`), `GET /activity/members/:identifier` one member as this viewer, `GET /activity/mine` the owner's entries with `sharing` (effective audience and `cappedBy`), and `GET /activity/mine/preview?audience=` **runs the same read as a hypothetical follower or non-follower**, so a preview cannot disagree with what the audience receives. `GET`/`PUT /activity/sharing` is a partial write of defaults, and `PUT /activity/entries/audience` refuses (404) an entry the owner does not have or one that never renders. `PROF-10` uses the pure helpers with this service's own `db`: blocked members are left out of each other's feeds and a member read answers 404 before anything is read. **The cursor is the last instant plus digests of the entries already returned at it**, because the facts of one workout share its end time and the database's string collation need not match JavaScript's; sources fetch `limit + 1 + seen` and exclude in memory. `RoutineSharingService.setVisibility` sets `sharedAt` only when a `PRIVATE` routine becomes visible (`sharedAtChange`); widening keeps it and unsharing keeps it, the routine's own visibility then capping the entry. Routines shared before SOC-03 have no `sharedAt` and produce no entry. Activity is signed-in only: there is no unguarded read, so "Everyone" means every member.

**A reaction is acknowledgement, and the activity read is its gate (SOC-05).** `ActivityEntryReaction` rows (migration `20260920120000_activity_reactions`, also applied by `scripts/prepare-analytics-test-db.ts`) are keyed by `(userId, entryKey)`, so choosing another replaces it and choosing the same one removes it — `nextReaction` in [activity-rules.ts](src/activity/activity-rules.ts) — and there is nothing to accumulate. `authorId` is stored when the reaction is accepted: an entry key belongs to one author by construction, and keeping it makes the read one query per page. **The summary travels inside the entry** (`summarizeReactions`), so a reaction can never be rendered on an entry the viewer was not allowed to see. `PUT /activity/entries/reaction` resolves the entry's author from the key, rebuilds that viewer's plan and answers **404** when it does not allow the entry — never 403, which would confirm it exists — and **400** when the author is the viewer, because acknowledging your own work is not what the feature is for. Counts leave out members either side of a block, since a number that included one would leak them through arithmetic, and **no list of who reacted is produced**: that is an identity surface with its own privacy question. Nothing else in the product reads these rows — no total, no rank, no ordering.

**A comment is discussion attached to one verified fact (SOC-06).** `ActivityComment` rows (migration `20260921140000_activity_comments`, also applied by `scripts/prepare-analytics-test-db.ts`) are keyed by the same stable `entryKey` a `SOC-05` reaction uses, because `SOC-03` entries are generated on read and that key is the only identity an activity has; `authorId` is the entry's owner, stored when the comment is accepted so the list read and the notification both know whose activity it hangs from without re-deriving the entry. **`resolveCommentableEntry` is the whole gate, and it is the reaction's gate reused** -- `GET`, `POST` and `DELETE /activity/entries/comments` all answer **404** for an entry the viewer may not see, never 403. Anyone who may read the entry may comment on it: a second permission would be a second answer to the same question. Unlike a reaction the **owner is allowed through**, because replying on your own activity is ordinary where acknowledging your own work is not. **Two people may delete**: the author and the activity's owner (`canDeleteComment`), and a moderator is deliberately neither -- `TRUST-04` hides through `ActivityComment.moderationHiddenAt`, so the enforcement record stays the only account of what a moderator did and nothing they touch is destroyed. A hidden comment is gone for everyone but the member who wrote it. **The count and the list are one answer**: both sides of a block and every hidden comment are excluded from each, so a number can never advertise a comment the viewer cannot open. `normalizeCommentBody` trims and refuses rather than truncating -- a comment clipped mid-sentence would misrepresent its author -- and the per-day budget is `ACTIVITY_COMMENTS_PER_DAY_MAX`. Reporting a comment is `ReportSubjectKind.COMMENT`; the queue shows its **body as the subject title**, because reviewing a reported comment means reading the words. `NOTIF-01` gained `ACTIVITY_COMMENT`, its first source that is a row rather than a training event and the first another member causes on purpose; it **carries no body**, because the notification outlives the comment and its author, the recipient or a moderator can each remove that text.

**Milestone achievements are immutable analytics events (ACH-01/DATA-02/ACH-04).** The shared catalog defines 25 thresholds across completed sessions, sets, external-load volume, current personal-record exercises and best streak days. `awardMilestoneAchievements` runs inside the account-scoped analytics writer and uses unique event keys, so finish retries and rebuilds do not duplicate `ACHIEVEMENT_UNLOCKED` or `STREAK_MILESTONE` events. `GET /achievements` reconciles a READY projection plus the bounded current-record count before reading; events recognized from pre-feature history use `sessionId = null`, `backfilled = true` and must never be presented as if an exact earned date were known. The same verified totals produce one first unearned milestone per category in catalog order; an exhausted category returns `nextMilestone = null` and `remaining = 0`. Keep the catalog finite unless the read limit and tests change together.

**Comeback recognition is a bounded event derivation (ACH-05).** `GET /achievements` reads at most the 501 most recent `SESSION_COMPLETED` events, derives from the first 500 and reports truncation when an older event exists. A comeback requires 14 full inactive local-calendar days followed by three distinct active dates within an inclusive 14-day window; same-day sessions count once. Recognition uses the third return session as its source, returns at most 20 newest results, and stores no duplicate award rows or migration state. ACH-08 reuses the same reconciled read for the optional `PublicUserProfile.achievements` ledger, but projects only the current rank, earned milestones and comeback summary. It is queried only when the existing achievements privacy rule grants access; next-rank requirements and milestone progress remain owner-only on `GET /achievements`.

### Runtime conventions

- `src/main.ts` polyfills `globalThis.crypto` via Node's `webcrypto` — this must stay as the very first thing in the file (before other imports run).
- Global route prefix is `api`; CORS origin comes from `FRONTEND_URL` env var (fallback `http://localhost:3000`).
- Global `ValidationPipe` has `transform: true` + implicit conversion, `whitelist: true`, `forbidNonWhitelisted: true` — DTO property types matter, and unknown request fields are rejected rather than ignored.
- Global rate limiting via `ThrottlerGuard` (`src/app.module.ts`), keyed on
  the caller through `clientIp` ([src/common/client-ip.ts](src/common/client-ip.ts)) rather than the
  default `req.ip`. **Anything that needs the caller's address asks that
  function.** Behind Railway's edge `req.ip` is an internal hop that *rotates*
  between requests (measured 2026-09-22: `100.64.0.2` through `100.64.0.8` for
  one client), so keying on it spread a single caller across buckets and the
  limit was never reached. `clientIp` reads `X-Real-IP`, which that edge sets
  per request and **overwrites rather than appends**, so a client cannot supply
  it; off Railway the header is absent and the connection address is used.
  That trust is a property of Railway's edge, not of the header -- on a host
  that appends, the value becomes client-controlled. Do not reintroduce
  hand-parsing of `X-Forwarded-For`, and do not swap this for a `trust proxy`
  hop count: a count is a guess about topology that fails silently when a hop
  is added or removed (TD-46).
- Built-in endpoints: `GET /health`, `GET /metrics` (Prometheus, IP-allowlisted
  through the same `clientIp`; `METRICS_IP_ALLOWLIST` is unset in production, so
  the list is `127.0.0.1,::1` and no external caller can match it).

## Closing a slice

The order the gates run in, and what each one is the only owner of. The
frontend's `CLAUDE.md` carries the same list; keep them saying the same thing.

1. **Contracts**, only when a shared shape changed: edit `../sunnsteel-contracts`, verify, publish, then install that version here and in the frontend.
2. **`npm run verify`, once, at the end**, with the dev server stopped. While iterating run `npm run lint`, `npm run typecheck` and `npm test`; the gate re-runs all of them plus the build and the build-import check. **The test tally is in `verify`'s own output** — do not run `npm test` again to read it.
3. **Migration**: `npx prisma migrate deploy` (and `npx prisma generate`) with the dev server stopped — it holds the Prisma query-engine DLL — and register the file in `scripts/prepare-analytics-test-db.ts` in the same change. CI's `migrations` job applies the whole chain to an empty Postgres with `migrate deploy`, then `migrate status`, then `migrate deploy` again: production runs the migration on every boot, so one that is not idempotent takes the service down on its second start rather than its first.
4. **Real-stack checks** against the running server, for what a Node test structurally cannot reach: Prisma `where` clauses, JSON-path filters, the order authorization runs in, cursors over real rows. A rule already covered by a pure test does not need a second assertion over HTTP. **A script that writes to the deployment database is never committed** — it is written, run, and deleted, so nobody can run it by accident later.
5. **Never write files in this repository while the frontend's `ui:regression` sweep is running.** `npm run start:dev` watches the tree and restarts; a restart mid-sweep fails every case in flight with the backend unreachable, and the run has to be discarded.
6. **Docs**: the roadmap closure with its decisions and what you did *not* verify, `CLAUDE.md`/`AGENTS.md` kept in sync, `../FEATURES.md` when a feature ships.
